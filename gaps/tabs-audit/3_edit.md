# Reader tab audit 3: EDIT tab (read-only audit)

Scope: the Edit tab's bottom row (`EditToolbar`, ui/reader/ReaderToolbars.kt:196-211), the property bar it shows while a tool is active, the Edit-content overlay (ui/edit/*, ui/nve/shapes, ui/nve/imgedit, core/edit/*), the "Edit tools" sheet (all edit5 tools), the quick sheets it opens (watermark, page numbers, properties, OCR) and the form designer entry.
Paths are relative to `app/src/main/java/com/smartdocs/editor/` unless noted.

In the user's screenshot (RTL), the row reads Organize | Document | Page numbers | Watermark | Text recognition | Link | Add image | Add text | Edit content. In code order (LTR) it is Edit content, Add text, Add image, Link, |, OCR, Watermark, Page numbers, Document properties, Organize, **Edit tools**, **Edit form fields**. The last two are scrolled off-screen in the screenshot.

## 3. Verified by running

Harness: kotlinc (embedded compiler from the earlier harness), real PdfBox-Android classes and android stubs from `scratchpad/arabicedit`. Files are in `scratchpad/tabsaudit/e3/` (`src/Main.kt`, `src/Shape.kt`, `out/`). Input: a copy of `chemistry/_الملخص_الشامل_في_الكيمياء_للصف_ثالث_ثانوي_الوحدة_الأولى.pdf` (2.72 MB).

- **E-01 confirmed.** `ContentEdit.addText` (the Edit content "add text" path; compiled engine classes from 26 Oct, same `EditIo.save`) gave: `src=2722330 out=2728353 commonPrefix=10 incremental=false`. The output shares only the first 10 bytes with the source. It is a full rewrite, not an incremental update, so any `/ByteRange` signature in the file would be broken. Every other Edit-tab writer uses the same `doc.save` pattern (code-read: `E5Io.save`, `PdfOps.saveTo`, `ImageEdit5.edit`, `DesignerState d.save`).
- **Not a defect (checked).** The quick Watermark text is shaped by `ArabicShaper.shape`; the content editor uses `Bidi.shapeVisual`. Compiled from current sources and run on "سري 2024", "مسودة Smart Docs" and "صفحة ١٢", the two gave identical visual sequences: digits and Latin keep their order and Arabic-Indic digits are not reversed. The concern in EditBidi.kt's header comment is fixed in ArabicShaper.
- **Strings:** a script checked 1461 `R.string` / `R.plurals` keys used by ReaderToolbars, ui/edit, ui/edit5, nve/shapes, nve/imgedit, the quick sheets and FormDesigner. None are missing in `values` (ar) or `values-en`. The only hard-coded UI texts are placeholders (`#FF5722`, `https://`, `1-3, 5`).
- **OK by code reading:** switching tab clears the tool and selection (ReaderScreen.kt:286). `content_edit` goes through the ReaderGuard MODIFY check (ReaderScreen.kt:204-205). "Edit text" from the selection bar checks MODIFY (NveSelection.kt:180). The LINK tool now creates real /Link annotations; the old fake-note fallback in ReaderDialogs.kt:128 is unreachable because `ReaderLinkPrompt` returns true. Rotation doesn't recreate the activity (manifest `configChanges`). Encryption is kept on full saves (`PdfOps.load` → `reprotect`, but see E-12). Content edits become one unified history step (`applyInPlace` → `swapFile` snapshot).
