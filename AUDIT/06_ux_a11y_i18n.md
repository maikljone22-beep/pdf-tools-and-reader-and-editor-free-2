## Findings

### UX-01 Language setting does not change the UI language; default "ar" forces RTL on English devices
- Type: bug
- Status: CONFIRMED
- Severity: High      Priority: P1
- Evidence:
  - `core/data/SettingsStore.kt:15`: `val language: String = "ar"` (default).
  - `ui/settings/SettingsScreen.kt:67`: `Choice(listOf("ar" to "العربية", "en" to "English"), s.language) { … copy(language = v) }`.
  - The only reader is `core/gaps6/G6Prefs.kt:20-24` (`else -> s.language == "ar"`) → `MainActivity.kt:46` `rtl = LayoutDir.isRtl(settings)` → `Theme.kt:64` `LocalLayoutDirection provides …`.
  - A grep finds no `setApplicationLocales`, `AppCompatDelegate`, `attachBaseContext`, `Locale.setDefault` or `res/xml/locales_config.xml`, and no `localeConfig` in the manifest.
- User impact / scenario:
  - A phone set to English opens the app. Strings come from `values-en` (English) but the layout is mirrored RTL, because the default language is "ar".
  - An Arabic phone where the user picks "English" keeps Arabic strings in an LTR layout.
  - Android 13+ per-app language settings cannot be used at all.
- Proposed fix:
  - Apply the locale with `AppCompatDelegate.setApplicationLocales(LocaleListCompat.forLanguageTags(lang))` (appcompat 1.6+) or `LocaleManager`, and add `res/xml/locales_config.xml` plus `android:localeConfig`.
  - Default `language` to "system" and derive RTL from `LocalConfiguration.current.layoutDirection` unless the user overrides it.
- Effort: M     Regression risk: Med     Dependencies: UX-03, UX-06
- Validation: device test with system en/ar × setting system/ar/en: strings and direction match. Unit test of `LayoutDir.isRtl` for "system".

### UX-02 "Save in original" overwrites the source document with no confirmation, no backup and a swallowed failure
- Type: data-integrity
- Status: CONFIRMED
- Severity: High      Priority: P1
- Evidence:
  - `ui/common/Components.kt:226-233`: the primary button `runCatching { app.documents.replaceOriginal(source, file) }; writeBack(source); onDismiss(); popBackStack(READER)`.
  - `core/files/DocumentRepository.kt:110-115`: `replaceOriginal` copies over the target, deletes the result copy, then calls `writeBack(target)`, which also pushes to the external SAF/cloud original.
  - `DocHistory` is only created inside `ReaderState`, so a tool's replace is not an undo step.
- User impact / scenario: The user runs Compress at LOW (`PageTools.kt:47-53`) or Flatten / Watermark from the reader and taps the big default "Save in original". The full-quality original, including the user's Drive/SAF copy, is replaced irreversibly. If the copy fails, the error is swallowed and the user is still sent back as if it had saved.
- Proposed fix:
  - Before replacing, copy the original into `history/<docId>` or the Trash (`Trash5.moveToTrash`).
  - Show a snackbar with Undo.
  - Surface `replaceOriginal` failures.
  - For lossy tools (compress/flatten/redact/sanitize), require a confirm dialog.
- Effort: S     Regression risk: Low     Dependencies: core/history
- Validation: instrumentation test (replace, then undo restores the byte-identical file). Fault-injection test that the failure shows an error.

- Type: bug
- Status: CONFIRMED (script)
- Severity: High      Priority: P1
- Evidence:

- Effort: M     Regression risk: Low     Dependencies: none

### UX-04 Long operations are modal with no cancel and no progress; Back is swallowed
- Type: usability
- Status: CONFIRMED
- Severity: High      Priority: P1
- Evidence:
  - `ui/common/Components.kt:135-136`: `ProgressDialog(...) { Dialog(onDismissRequest = {}) …` cannot be dismissed and has no button.
  - `ToolRunner` (`Components.kt:160-183`) keeps no `Job` and offers no `cancel()`.
  - `ToolScaffold` shows an indeterminate dialog (`ToolCommon.kt:83`: `ProgressDialog(runner.message…)`, with no `progress`).
  - Used by 31 ToolScaffold screens + 40 `ProgressDialog(` sites (merge, split, compress, convert-from-PDF, watermark, redact, sanitize, digital sign, scanner…).
  - By contrast, Quick actions support `cancellable = true` (`QuickController.kt:185`).
- User impact / scenario: Compressing or converting a 300-page PDF freezes the screen behind an unclosable spinner for minutes. The user can only kill the app, which may leave partial output files.
- Proposed fix:
  - Store the `Job` in `ToolRunner`, add `cancel()` (which deletes the partial `out`), and give `ProgressDialog` a Cancel button plus `onDismissRequest = cancel`.
  - Pass a determinate progress where the core already reports it (`Optimizer.optimize { d, t -> }`).
- Effort: M     Regression risk: Med     Dependencies: core ops must be cooperative (`ensureActive()` in page loops)
- Validation: device test: start Compress on a big file, Cancel returns within 1 s, no output file remains.

### UX-08 The same feature behaves differently depending on the entry point (compress / OCR / watermark / protect / compare)
- Type: usability
- Status: CONFIRMED
- Severity: Medium      Priority: P2
- Evidence:
  - **Compress**:
    - `tool/compress` (`PageTools.kt:47-53`): no password argument (encrypted PDFs fail), no cancel, no "no gain" guard, so it can produce a larger file.
    - Quick COMPRESS (`QuickController.kt:183-193`): password, cancellable, and deletes the output when `out.length() >= before`.
    - `tool/optimize` (`OptimizeExportScreens.kt:76-99`): audit + progress.
    - In the Tools grid the two cards share `Icons.Default.Compress` and sit in different groups ("Organize" `ToolsScreen.kt:52` vs "Read" `:82`).

- User impact / scenario: The user's result depends on which of 2–4 doors they used. "Reduce size" from Tools can make a file bigger, while the same action from the reader refuses. 55 tools plus 20 hidden e5 tools make the grid hard to scan.
- Proposed fix:
  - Make each feature one engine / one screen with modes (Compress = basic/advanced tabs, OCR = single/batch).
  - Have the Tools cards deep-link to a mode.
  - Remove the duplicate ids from `allTools`.
  - Port the no-gain guard and password into `CompressScreen`.
- Effort: M     Regression risk: Med     Dependencies: UX-04
